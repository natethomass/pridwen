# Under the hood and cutting off

firewalld is a front end; underneath, it programs nftables in the kernel.
`sudo nft list ruleset` shows the actual rules it generated, which is useful when
you want to see exactly what a zone became. Hand-written `iptables` rules are
ignored or overwritten here, so `firewall-cmd` is the tool that owns the ruleset.

Two blunt controls are worth knowing for incidents. `--panic-on` drops every
packet in both directions, isolating the host completely, and `--panic-off`
restores the zone rules. Because panic mode also cuts an SSH session you might be
in, use it on a console or when you are prepared to lose the connection.

```
$ sudo nft list ruleset | head
$ sudo firewall-cmd --panic-on     # total isolation
$ sudo firewall-cmd --panic-off    # back to normal
```

Stopping firewalld entirely is the opposite mistake: it opens every listening
socket to the network at once. If one service is unreachable, the fix is to open
its one port, not to switch the firewall off. On a Range host, panic mode is a
clean way to isolate a suspected-compromised machine while you investigate,
keeping it powered on so its memory and connections remain as evidence.

## Try it

1. Run `sudo nft list ruleset` and find the drop policy firewalld created.
2. On a test host with console access, try `--panic-on` then `--panic-off`.
3. Explain why stopping firewalld is worse than opening a single port.
4. Describe when isolating a host with panic mode helps an investigation.
