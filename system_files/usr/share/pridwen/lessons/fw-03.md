# Under the hood and cutting off

firewalld is a front end. It does not filter packets itself; it takes your zones
and services and writes them into **nftables**, the packet-filtering framework
inside the Linux kernel. Knowing that one fact explains two things you will
meet on a job: why old `iptables` commands from a tutorial do nothing useful
here, and how to see the real rules when you want to be sure what a zone became.

This lesson also covers the two blunt controls that exist for incidents. Panic
mode cuts a host off from the network in both directions with one command, and
stopping firewalld does the opposite, exposing everything at once. One of these
is a tool an incident responder reaches for on purpose; the other is the mistake
people make when a service will not connect. Telling them apart is the point of
the secure tier.

## Words you'll meet

- **nftables**: the kernel's packet-filtering framework; the rules that actually decide each packet's fate live here.
- **`nft`**: the command that reads and writes nftables rules directly; `nft list ruleset` prints all of them.
- **iptables**: the older framework and command that nftables replaced; on Fedora it is a compatibility layer at best.
- **ruleset**: the complete set of nftables tables, chains and rules loaded in the kernel.
- **chain**: an ordered list of rules inside a table; a packet walks down a chain until a rule decides.
- **policy** (in nftables): what a chain does with packets no rule matched; `drop` discards, `accept` lets through.
- **panic mode**: a firewalld state that drops every packet in both directions, isolating the host.
- **listening socket**: a program waiting for connections on a port, as shown by `ss -tlnp`.

## How it works

`nft list ruleset` prints the whole ruleset. It is root-only, so it needs
`sudo`, and it is long, so pipe it into `head` (the first lines) or `less`
(page through it).

```
{user}@{host}:~$ sudo nft list ruleset | head -20
table inet firewalld {
	chain filter_INPUT {
		type filter hook input priority filter + 10; policy accept;
		ct state { established, related } accept
		ct status dnat accept
		iifname "lo" accept
		ct state invalid drop
		jump filter_INPUT_ZONES
		reject with icmpx admin-prohibited
	}
	chain filter_INPUT_ZONES {
		iifname "wlp2s0" goto filter_IN_drop
		goto filter_IN_drop
	}
	chain filter_IN_drop {
		jump filter_INPUT_POLICIES_pre
		jump filter_IN_drop_pre
		jump filter_IN_drop_log
		jump filter_IN_drop_deny
		jump filter_IN_drop_allow
```

Read it top down. `table inet firewalld` is the table firewalld owns (`inet`
means it covers both IPv4 and IPv6). `chain filter_INPUT` is where inbound
packets enter. `ct state { established, related } accept` is the rule that lets
replies to your own connections through, which is why browsing works in the
drop zone. `iifname "lo" accept` trusts the loopback interface, the machine
talking to itself. Then `jump filter_INPUT_ZONES` hands the packet to the zone
chains, and `iifname "wlp2s0" goto filter_IN_drop` sends anything arriving on
the wireless card to the drop zone's chain. Further down, `filter_IN_drop`
ends in a rule that drops whatever the allow chain did not accept. The zones
you read with `firewall-cmd` are exactly this.

Because firewalld owns that table, hand-written `iptables` rules are the wrong
tool. They may land in a separate compatibility table that firewalld ignores,
or firewalld overwrites them at its next reload. `firewall-cmd` is the tool
that owns the ruleset, and `nft list ruleset` is how you check what it wrote.

Now the blunt controls. Panic mode drops every packet in both directions.

```
{user}@{host}:~$ sudo firewall-cmd --panic-on
success
{user}@{host}:~$ sudo firewall-cmd --query-panic
yes
{user}@{host}:~$ ping -c 1 1.1.1.1
PING 1.1.1.1 (1.1.1.1) 56(84) bytes of data.

--- 1.1.1.1 ping statistics ---
1 packets transmitted, 0 received, 100% packet loss, time 0ms
{user}@{host}:~$ sudo firewall-cmd --panic-off
success
```

`--query-panic` answers `yes` while it is on. The `ping` (`-c 1` sends one
packet) gets no reply because outbound traffic is dropped too; that is the
whole point. `--panic-off` restores the zone rules exactly as they were. Panic
mode is runtime only: it does not survive a reboot, which is a safety net.
Because it also cuts an SSH session you might be sitting in, use it from the
machine's own console, or when you are prepared to lose the connection and
walk over.

On a Range host, panic mode is a clean way to isolate a machine you suspect is
compromised while you investigate. Pulling the power would destroy the evidence
in memory and close every connection an attacker had open; panic mode keeps the
host powered on with its processes and memory intact, and simply stops it from
talking.

Stopping firewalld is the opposite action, and it is the mistake. With the
daemon stopped, the `firewalld` table is removed and every listening socket in
`ss -tlnp` is reachable from the network at once. If one service is
unreachable, the fix is to open its one port, `sudo firewall-cmd
--add-port=8080/tcp`, not to switch the firewall off. The Coach says exactly
that under a `systemctl stop firewalld`.

## When it goes wrong

`nft: command not found` or `Operation not permitted` from `nft` means it was
run without `sudo`; the ruleset is readable only by root.

`iptables: No chain/target/match by that name` or rules that seem to apply and
then vanish means iptables is fighting firewalld. Delete nothing by hand; use
`sudo firewall-cmd` for the change and `sudo nft list ruleset` to confirm it.

Your SSH session freezes right after `--panic-on`. That is panic mode doing its
job, and the session will not come back on its own. Reach the console (or a
Range host's virtual console) and run `sudo firewall-cmd --panic-off`, or
reboot, since panic mode is not saved. `pridwen why` under the frozen command
says the same.

## Try it

1. Type `sudo nft list ruleset | grep -c .` to count the lines firewalld generated; expect a few hundred.
2. Type `sudo nft list ruleset | head -20` and find the `ct state { established, related } accept` line and the `goto filter_IN_drop` line.
3. On a Range host with console access, type `sudo firewall-cmd --panic-on`, then `sudo firewall-cmd --query-panic` and expect `yes`.
4. Type `ping -c 1 1.1.1.1` and expect `100% packet loss`.
5. Type `sudo firewall-cmd --panic-off`, then `ping -c 1 1.1.1.1` again and expect a reply.
6. Explain in one sentence why stopping firewalld is worse than opening a single port, and in another when isolating a host with panic mode helps an investigation.

## Remember

- firewalld writes nftables; `sudo nft list ruleset` shows the real rules, and `iptables` commands are not the tool here.
- `--panic-on` drops everything both ways, including your SSH session; `--panic-off` restores the zones, and neither survives a reboot.
- An unreachable service means one port to open, never `systemctl stop firewalld`.
