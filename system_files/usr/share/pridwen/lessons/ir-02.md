# Preserve before you change

Everything you do on a live host changes it. Opening a file updates its access
time, running a command adds a process and a journal line, and stopping the
wrong thing erases what it was doing. So response means capturing state before
you alter it, in an order that saves the most fragile evidence first. Memory and
running state vanish on reboot; disk survives. You record the volatile things
first and the durable things later.

On a job this is called the order of volatility, and it is what lets an
investigation be trusted afterwards: someone can show what the machine looked
like before anyone touched it. On Pridwen you build the capture on your own
host, where it is a harmless snapshot, and then on a Rocky 9 Range host you own,
arriving in milestone M4, where the snapshot is the evidence a scenario is graded
on.

## Words you'll meet

- **volatile**: state lost on reboot: memory, processes, sockets, logged-in sessions.
- **order of volatility**: capture the most short-lived evidence first, the most durable last.
- **capture**: saving a command's output to a file so it can be read later, unchanged.
- **timestamp**: a date and time written into the file name so captures sort in order.
- **shell variable**: a name holding a value, set with `name=value` and read with `$name`.
- **footprint**: a change you made yourself, which must be recorded so it is not mistaken for the intruder's.

## How it works

Restating the essential from the last lesson: look at sessions, connections and
processes before acting. Now save those looks to files. First make a directory
for the case and put the current time in a variable so every file shares one
stamp.

```
{user}@{host}:~$ mkdir -p {home}/ir
{user}@{host}:~$ ts=$(date +%F-%H%M)
{user}@{host}:~$ echo $ts
2026-09-07-1118
```

`date +%F-%H%M` prints the date as `YYYY-MM-DD`, a dash, then hours and minutes.
`$(...)` runs the command inside and substitutes its output, so `ts` now holds
`2026-09-07-1118`, and `$ts` anywhere on a later line expands to that. A
variable set this way lasts for this shell only, which is fine.

Now the captures, most volatile first. `ps auxww` lists every process for every
user in the traditional wide format; the doubled `w` means never truncate the
command line. `ss -tanp` lists all TCP sockets (`-a`, listening and connected),
numeric, with processes, and needs `sudo` to name other users' processes.
`loginctl list-sessions` records who is logged in. `journalctl --since -2h`
pulls the last two hours of the journal.

```
{user}@{host}:~$ ps auxww               > {home}/ir/$ts-ps.txt
{user}@{host}:~$ sudo ss -tanp          > {home}/ir/$ts-ss.txt
{user}@{host}:~$ loginctl list-sessions > {home}/ir/$ts-sessions.txt
{user}@{host}:~$ journalctl --since -2h > {home}/ir/$ts-journal.txt
{user}@{host}:~$ ls -l {home}/ir
total 1288
-rw-r--r--. 1 {user} {user} 1301212 Sep  7 11:18 2026-09-07-1118-journal.txt
-rw-r--r--. 1 {user} {user}   42117 Sep  7 11:18 2026-09-07-1118-ps.txt
-rw-r--r--. 1 {user} {user}     312 Sep  7 11:18 2026-09-07-1118-sessions.txt
-rw-r--r--. 1 {user} {user}    2890 Sep  7 11:18 2026-09-07-1118-ss.txt
```

Each `>` writes the command's output into a new file. The `ls -l` listing shows
four files with one stamp, and the sizes tell you at a glance that the journal
is the big one and the sessions file is a few lines. `sudo ss` writes the file as
you, not root, because the redirection is done by your shell before `sudo` runs;
that is why the owner column says `{user}`.

Now record your own footprint. Note the time you started, the host, and every
command you have run so far, in a notes file that lives with the captures.

```
{user}@{host}:~$ cat >> {home}/ir/$ts-notes.txt <<EOF
$(date +%T) started on {host}; suspected: unexpected bash on port 4444
$(date +%T) captured ps, ss, sessions, journal (-2h) as $ts-*.txt
EOF
{user}@{host}:~$ cat {home}/ir/$ts-notes.txt
11:19:02 started on {host}; suspected: unexpected bash on port 4444
11:19:02 captured ps, ss, sessions, journal (-2h) as 2026-09-07-1118-*.txt
```

`>>` appends instead of replacing, so you can keep adding lines through the
hour. `date +%T` is the time as `HH:MM:SS`. Every later action gets a line, so
that when the journal shows a command at 11:23, you can tell whether it was
yours.

With the picture saved you can afford to look closer at one suspect. `ls -l
/proc/<pid>/cwd` shows a process's working directory, `ls -l /proc/<pid>/fd`
its open files and sockets, and `cat /proc/<pid>/environ | tr '\0' '\n'` its
environment; each is a read, not a change, and the original captures still
stand if the process exits while you look. Only after capturing do you consider
stopping anything, which is the next lesson. The order is the same whether the
scenario is a compromised `web-01` or a real machine: volatile first, disk later,
and a written record of your own steps throughout.

## When it goes wrong

`bash: {home}/ir/-ps.txt: No such file or directory` or a file named just
`-ps.txt`. The `ts` variable is empty, usually because it was set in a different
tab; variables belong to one shell. Set `ts=$(date +%F-%H%M)` again in this tab.

`Permission denied` writing to `{home}/ir`. The directory does not exist or is
not yours. `mkdir -p {home}/ir` and check with `ls -ld {home}/ir`.

`ss` output with empty `users:()` columns. It ran without `sudo` and could only
name your own processes. Recapture with `sudo ss -tanp` and note in the notes
file that the first capture was partial, rather than deleting it.

## Try it

1. Run `mkdir -p {home}/ir` and `ts=$(date +%F-%H%M)`, then `echo $ts` to confirm the stamp.
2. Capture `ps auxww`, `sudo ss -tanp`, `loginctl list-sessions` and `journalctl --since -2h` to `{home}/ir/$ts-*.txt`.
3. Run `ls -l {home}/ir` and check that all four files share the stamp and that the journal is the largest.
4. Append two lines to `{home}/ir/$ts-notes.txt` with `date +%T`: when you started and what you captured.
5. In a second tab start `bash -i`; from the first, find its pid in `ps` and read `ls -l /proc/<pid>/cwd` without stopping it. Add a notes line.
6. Explain the order of volatility in one sentence: why memory and sockets were captured before anything on disk.

## Remember

- Capture volatile state first: processes, sockets, sessions, then the recent journal.
- One timestamp in every file name, and a notes file that logs your own actions with `date +%T`.
- Read a suspect through `/proc` after the capture; change nothing until the picture is saved.
