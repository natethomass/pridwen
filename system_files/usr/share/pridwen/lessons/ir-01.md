# The first hour

When a host starts behaving strangely, the first hour has a shape: find out who
and what is on the machine, preserve what you see, and decide whether to isolate
it. Two instincts fight you. One is panic, which makes you act before you look.
The other is the reflex to reboot and make it stop. Both destroy the very
evidence you need, so the first discipline of incident response is to slow down
and observe.

On a job, the first hour decides whether the investigation that follows has
anything to work with. On Pridwen you learn the moves on your own host, where the
"strange" host is simply yours and every answer is boring, so that when a Rocky 9
Range host you own, arriving in milestone M4, is scripted to misbehave, the
commands are already in your hands and your attention is free for the picture.

## Words you'll meet

- **session**: one login, whether at the screen, in a terminal, or over SSH; `loginctl` tracks them.
- **established connection**: a TCP conversation that is open right now between this host and another.
- **volatile**: state that vanishes on reboot, such as memory, running processes and open sockets.
- **elapsed time**: how long a process has been running, shown by `ps` as `etime`.
- **isolate**: cut a host off the network while leaving it running.
- **thread**: the one unexplained thing you pull on first.

## How it works

Start with who is here. `w` prints the logged-in users with where they came from
and what they are running. `loginctl list-sessions` prints the same from
systemd's point of view, including sessions that have no terminal.

```
{user}@{host}:~$ w
 11:02:10 up  2:14,  2 users,  load average: 0.31, 0.22, 0.19
USER     TTY      FROM             LOGIN@   IDLE   JCPU   PCPU WHAT
{user}   tty2                      08:48    2:14m  0.04s  0.04s /usr/libexec/gnome-session-binary
{user}   pts/0                     10:55    0.00s  0.03s  0.00s w
{user}@{host}:~$ loginctl list-sessions
SESSION  UID USER    SEAT  TTY   STATE  IDLE SINCE
      2 1000 {user}  seat0 tty2  active no   -
      5 1000 {user}  -     pts/0 active no   -
```

Reading `w` back: the header line has the time, the uptime, and the load. Then
one row per session: the user, the terminal (`tty2` is the graphical login,
`pts/0` is a Ptyxis tab), where they came from (`FROM` is empty for local
sessions and holds an address for SSH), when they logged in, and what they are
running. `loginctl` adds the session number and the seat. Two sessions, both
yours, both local, is the normal picture on a desktop. A row with a `FROM`
address you do not recognise, or a user you did not expect, is the first thread.

Next, what is the machine talking to. `ss -tnp state established` lists TCP
sockets (`-t`) with numeric addresses (`-n`) and the owning process (`-p`, which
needs `sudo` to name other users' processes), filtered to established
connections only.

```
{user}@{host}:~$ sudo ss -tnp state established
Recv-Q Send-Q Local Address:Port      Peer Address:Port     Process
0      0      192.168.122.15:49212    140.82.112.4:443      users:(("firefox",pid=3320,fd=88))
0      0      192.168.122.15:38874    203.0.113.9:4444      users:(("bash",pid=9917,fd=3))
```

Columns: bytes waiting in each direction, the local address and port, the peer
address and port, and the process. The first row is a browser talking to a web
server on port 443, which is normal. The second is `bash` holding a connection to
port 4444 on an outside address, which is not: a shell does not open network
sockets unless something told it to. On a Range scenario this is the classic
reverse shell, and on your own host you will see only rows like the first.

Then, what is running, ordered by when it started, because the newest unexpected
process is usually the one that matters.

```
{user}@{host}:~$ ps -eo pid,user,etime,cmd --sort=start_time | tail -n 5
   9902 {user}       03:12 /usr/bin/python3 /usr/lib/pridwen/pridwend
   9917 {user}       01:40 bash -i
   9941 {user}       00:31 /usr/bin/ptyxis-agent
   9960 {user}       00:02 ps -eo pid,user,etime,cmd --sort=start_time
   9961 {user}       00:02 tail -n 5
```

`ps -e` means every process, `-o` picks the columns (process id, owner, elapsed
time, command line), and `--sort=start_time` orders oldest first, so `tail -n 5`
shows the five newest. `etime` reads minutes and seconds, or `days-hours:min:sec`
for long runners. Here `bash -i`, an interactive shell started a minute and forty
seconds ago with no terminal of yours behind it, is the same process id as the
4444 connection above. Two views, one thread.

Write down what you find as you go, in a plain file with the time, because
memory blurs under pressure and the next lesson turns these notes into
preserved evidence. What you do not do yet is kill the process or reboot. A
reboot clears memory, running processes and open sockets, which are exactly the
three things you just looked at; killing the process loses what it was connected
to. The goal of the first hour is not to fix but to understand enough to act
without destroying the record.

## When it goes wrong

`ss` shows `users:()` empty or missing on some rows. You ran it without `sudo`,
so it could only name your own processes. Run `sudo ss -tnp state established`.

`error: unknown sort specifier` from `ps`. The sort key is misspelled; it is
`start_time` with an underscore. `pridwen explain ps` annotates the flags.

`loginctl list-sessions` shows a session in state `closing`. That is a login
that ended but still has a process attached, common after closing a terminal.
It is not suspicious on its own; check what process holds it with `loginctl
session-status <number>`.

## Try it

1. Run `w` and `loginctl list-sessions` on your own host. Match each row to a window or tab you have open.
2. Run `sudo ss -tnp state established` and name the program behind each row; a browser and Pridwen's own services are the expected ones.
3. Run `ps -eo pid,user,etime,cmd --sort=start_time | tail -n 10` and pick out the newest process you did not start yourself.
4. Open a second Ptyxis tab, run `bash -i`, and repeat step 3; find it by its `etime`.
5. Write three lines to `{home}/pridwen/ir-notes.txt`: the time, what you found, and what you did not do.
6. On a Range host under a scenario, repeat steps 1 to 3 and find the session, connection and process that do not belong.

## Remember

- Look before you act: sessions with `w` and `loginctl`, connections with `ss -tnp state established`, processes with `ps --sort=start_time`.
- The newest unexpected process and the connection it holds are usually one thread.
- A reboot or a hasty kill destroys memory, processes and sockets, which are the evidence.
